# Quality gates

Mandatory for implementation self-check and review, including repairs and non-spec work. Read [principles](../principles.md), [conventions](../conventions.md), the selected profile and the owning project's contracts first. For backend or frontend changes, read the corresponding sections below and [concrete examples](examples.md); for project-specific differences, read [local contracts](local-contracts.md). Documentation changes load the spec/completion section and [context policy](../context.md).

Record `pass`, `fail` or `not applicable` for every applicable check with `file:symbol` evidence or a concrete inapplicability reason in ignored work state. Inventory the complete changed and untracked surface, including private helpers, constructors, typeclass instances, calls and suites; a maintainer's highlighted lines are not the scope limit. Existing passing tests, precedent resemblance and compliant line counts do not establish quality.

## Architecture

| Check | Required evidence | Blocking example and consequence |
| --- | --- | --- |
| Continuity | Trace trigger → authoritative state → acquisition → transformations → retained result → publication → all consumers; try reuse, then evolution, before separation. | A second reader rebuilds an already prepared snapshot for another endpoint: divergent selection and normalization now have two owners. |
| Ownership | Map each operation to an independently changing responsibility; read implementation, callers and owning suites in full. | A generic client owns different resources' pagination and selection; thin resource wrappers still leave their decisions centralized. |
| API cohesion | Inspect actual public/private calls and construction; identify each input's supplier, consumed facts, enabled decisions and result consumer. Inspect more than five fields/inputs for siblings, cohesive groups or distinct ADT states. | An aggregate bag hides unrelated inputs; an operation accepts another operation's success/failure envelope instead of the facts it uses. |
| Dependency lifetime | Inventory every constructor/method parameter; fixed collaborators/settings belong at construction, changing facts at invocation. | Static normalization settings are passed with every item, or a caller preclassifies a collaborator's uncertainty and loses its evidence. |
| Associations | Trace typed keys, cardinality, empty/unavailable entries, duplicates and precedence through projections; prove order-sensitive outcomes. | Parallel chapter/photo lists lose identity when one entry is absent; a sort changes first-winner spelling without an owning rule. |
| Effects | Name the concrete I/O, resource, concurrency or capability work for each effectful API; pure operations return plain data. | A pure classifier returns `F[Result]` solely by lifting its computed answer; callers inherit unnecessary sequencing. |
| Valid states | List invalid combinations and types excluding them; identify the enforcing owner for cross-value guarantees. | Independent status, optional ID and evidence fields permit a confirmed item without identity; a consumer repeats a domain-valid port's kind check. |
| Policy | Identify configurable data's authority, reader, update path and failure semantics. | An editable normalization catalog becomes a constant or static setting, losing its repository-backed lifecycle. |
| Necessary layers | Try removing every added module/method/argument through existing contracts or loaded data; justify batch/scope independently of identity. | “Metadata preparation” merely orchestrates our ports but is called an external adapter; extra HTTP calls alone do not justify a new client. |
| Test boundary | Identify production owner, public operation, scenario, substitutes and real external boundary crossed. | A service calling injected ports is labeled a seam; a real server running beside it does not prove that service crosses HTTP. |

Challenge sharing in both directions: which concrete change must make callers evolve together, and which must remain local? Share knowledge whose divergence is a bug; keep independently changing resource rules local even when their endpoint/result shapes match. Assess the resulting architecture together after local checks: acquisition, retained evidence and publication have coherent owners, not unions of unrelated workflows controlled by flags.

A seam crosses the adapter's actual HTTP exchange, database engine, filesystem, process or configuration representation. Driving HTTP tests send real requests with the application service substituted; driven HTTP tests use the real remote boundary in isolated state. An operation coordinating our own ports has a component suite. Pure single-owner mapping stays private; stateless business policy still belongs behind its owning module.

## Readability and suites

- Re-derive each changed module's whole suite from its current observable contract. Extend, merge, retarget or delete existing scenarios; add a new case only for genuinely new behavior without an owning case.
- Consolidate tests differing only in inputs into an intelligible table: name row fields by their behavioral roles, interpolate the actual domain variant and assert typed expected outcomes. Positional booleans whose meaning requires decoding fail this check.
- Inspect every grown method, block and chain for sibling abstraction levels; callers receive needed facts instead of reconstructing low-level details from anemic results.
- Measure methods near 7–10 lines, units beyond a screenful and suites near 3× production size. Split independently required responsibilities or record a cohesive reason; trimming tests or extracting pass-through wrappers does not satisfy the check.
- Inspect assignments, chains, calls and lambdas after formatting. Keep fitting expressions together; move a chained call to a new line when that keeps tuple/type arguments intelligible. Name meaningful conditions and bulky nested expected/result values, not incidental intermediates solely to reduce line counts.
- Keep comprehension generators contiguous. Separate Arrange, Act and Assert with blank lines outside the comprehension; surrounding declarations and assertions remain visually distinct.
- Declare scenario data in semantic order, grouped by the state it explains rather than by type. Name values for established meaning (`orderedChapters`, `wateredPlantOperations`), not a helper's mechanics (`processed`, `watered`).
- Build a complete named expected value immediately above the normal one-line assertion; safely name a bulky actual expression too. Preserve result variant, flags, identity, order and associations instead of checking a convenient field.
- Use `should` names in the exposed domain vocabulary; interpolate actual variants such as `s"should return ${WateringAttention.Current} ..."` so renamed values cannot leave stale prose.
- Read the actual reference suite before adapting its setup. Suite-local builders own meaningful construction; no fixture carriers, assertion wrappers, loaders or callback setup frameworks hide the scenario.

## Backend inventory

- Inventory pure/effectful APIs, including typeclass instances. Domain owns value constraints and independently true derivations; adapters own external parsing/normalization and source assembly; application operations own aggregate construction, selection and lifecycle decisions.
- A global ordering choosing retained spelling, precedence or winners needs a fundamental domain invariant. Chronology/book structure can qualify; one screen's selection policy belongs to its supplying operation.
- Business modules use trait → companion `make` → `private final class Live<CompanionObjectName>` → companion-owned operation results. Pure domain values need no artificial module. Inventory every public/package-visible helper: factories or mechanical utilities only, with real callers and a shared invariant.
- Inspect each operation's unwrapped return contract under the selected [local contract](local-contracts.md). Operation-owned results expose success, expected short-circuit and failure distinctly; helpers return narrow data, not the caller's public envelope. Companion failures are `Failure`; top-level types are shared/config values such as `AlbumPageSize`.
- Inventory capabilities and concrete interpreters: business collaborators are substitutable at their owner, runtimes/logging bind only in composition. Fixed settings are parsed once into consumer-needed types.
- Inventory every changed comprehension: multiple dependent steps stay linear; Typelevel single-generator pure results use `.map`. One physical line per statement is a design inspection signal: first check API cohesion and abstraction, then hoist cohesive SQL/expressions or meaningful dependency construction. A long named parameter bag, forced long line or pure `.pure[F]` wrapper does not resolve it.
- A comprehension mixing `<-` and `=` needs a recorded same-abstraction-level justification. Independently changing algorithms retain their own owners rather than becoming an orchestrator's private algorithm collection.
- Resource acquisition/use/release uses the stack's resource-safe primitive; integration suites own that resource directly. State-dependent writes check and commit against current state, with port-level guarantee and concurrent real-adapter scenarios; an earlier read plus atomic write is insufficient.
- Inventory method/helper/builder names for action or predicate verbs (`findCreationConflict`, `hasCreationConflict`). Optional fields/values/parameters use `maybe`; direct-style Either values use `Result`. Name literals, `Nil`, collections, booleans, dates and optional arguments when types conceal roles, including test arrangements and captured calls.
- Public APIs declare return types; private members omit them except Unit. Runtime default arguments remain forbidden by the existing full linter rules. Use imports, destructure only if all fields are needed and use named tuple patterns rather than `._1`.
- Keep shared codecs pure/bidirectional with at least two actual consumers and one shared representation invariant. Prefer direct declarative codecs; boundary-local DTOs exist only when the format cannot be expressed cleanly without them.
- Inventory changed refinement declarations and every explicit/implicit proof site, including `autoRefine`. Production domain/usecases retain required guarantees; non-core/tests retain only consumer-needed proofs with `file:symbol` rationale.
- Domain-valued arranged inputs and substituted port responses stay validated before the action. Reuse checked values for complete domain expectations; underlying text/numeric catalogs compare against safely widened actual values.
- Count construction/conversion sites, not aliases or runtime records, when reducing repeated proofs. Preserve rejection-specific proofs, constraints, complete assertions and strict gates; casts, assumptions and fixture frameworks are not reductions.
- Suite order is meaningful reusable data → scenarios → at most one observation `Refs` per scenario → builders. Responses/failures/clocks are builder inputs, never Refs contents; observation roles remain named. Omit Refs when no calls/effects are asserted.
- Builders create substitutes for actual collaborators; pure modules need none. Share only nontrivial multi-suite setup owning knowledge, not constructor aliases or small independent domain examples. Direct-style substitutes use the existing TestImplicits/Mocks contract.
- Suites name real runtime boundaries, not result ADTs, private traversals or feature buckets. Component tests substitute ports; adapters prove their own shape/order/validity once at real seams rather than through each consumer. Structural architecture policy uses one plainly named ArchitectureTest with one test.
- Suppressions require site-specific proof, smallest declaration scope and full rule ID; for example `minBy` after a proven nonempty guard. A reason does not authorize disabling an unsafe operation or weakening a gate; comment/directive exceptions follow the selected profile and explicit local contract.
- Preserve configured compiler, formatter, lint, architecture, dependency-update and coverage gates. Pin introduced dependencies and demonstrate their needed capability. Existing zero-warning/100%-coverage and contract-generation requirements stay local, not downgraded to recommendations.

## Frontend inventory

- Export pure validation/derivation/formatting as plain functions tested directly against their branch table; component tests prove rendering/wiring rather than repeating the same table.
- A disabled control explains why using the same predicate and an `aria-describedby` association. UI invariants mirror the actual backend contract and fail closed, rejecting rather than silently repairing.
- Tests use accessible roles/names and real events. Test IDs, CSS classes, element structure and impossible staged states do not establish user behavior.
- Derived state uses accessors/createMemo; Show handles conditional rendering, For keyed identity and Index positional/primitive rows.
- Prove expansion, collapse, success, failure and pending transitions retain accessible state and focus on a persistent control or rendered status. Layout uses structural boxes, fluid bounds and explicit narrow-width behavior rather than decorative layers.
- Read current styles/dialog/feedback/toolbar precedents. Content remains primary, editing chrome quiet, actions visibly grouped, wording sentence case, saved names authoritative and proper names/catalog content preserved.
- Toolbar icons retain the established thin-stroke language, hover text and equivalent accessible names. Navigation/editing/viewing remain distinct; interaction-owned shortcuts coexist with text entry/native controls.
- Preserve compiler/reactivity-required bindings and the selected import contract. A genuinely guarded unreachable branch may use the repository's exact coverage directive with proof; reachable failures require user-path coverage.

## Spec and completion

- Read the exact template and whole proposal before checking. Record feature/investigation classification and matching branch naming where a branch is created; current living model is authority, archived proposals history unless explicitly designated.
- What/why and acceptance are nonempty. Doc Sync is explicit: document/section/durable knowledge delta, or `None`; each unchanged owner is omitted. Distinct sections add unique facts, not filler or repeated acceptance prose.
- Evidence names an observed experiment finding or a specific checkable reason none was needed; “already understood” is not grounding. Experiment-backed design notes and real alternatives reflect the findings; investigations establish the cause and rejected hypotheses from evidence.
- Keep behavior/contract altitude throughout: observable intent and guarantees, not signatures, module layouts, library availability or diff walkthroughs. Explain lossy versus lossless semantics rather than “the JDK lacks a quality dial”; paths are authoritative pointers only.
- Changed domain/persistence/boundary guarantees identify enforcing owners, trigger-to-committed-state flow, failure order and UI delivery. Separate database-enforced constraints from use-case decisions and verify their mechanisms against source.
- Draft structure first; diagrams/tables answer significant flow/contract questions and prose fills only their gaps. Each criterion states one short observable behavior with relevant failure, boundary and accessibility cases.
- Inspect rendered proposal paragraphs/list items for at most two lines; direct-style prose also has at most two sentences per paragraph. Run the executable owning Markdown wrapping checker on every changed Markdown file; source wrapping failure blocks review.
- Compare with the closest approved precedent's scope and concision; a smaller change with equally large or larger prose needs pruning. Invariants are pre-existing guarantees, tradeoffs name an actual cost/bearer and out-of-scope entries answer likely questions; omit empty sections and roadmap inventories.
- Map every criterion and enumerated edge case to a passing named scenario at its owning boundary; deferred slice criteria have explicit owners. Contractual external names are preserved, while internal design follows caller needs rather than mistaken spec implementation nouns.
- Verify each slice compiles and passes its gates without unpublished later code; call-site migrations ship with their owner and each retained API has a concrete approved consumer. Amend changed scope/guarantees through execution's authorization rule before tests/code.
- During spec implementation, keep Doc Sync deltas accurate and deferred. After all implementation merges, compare actual delivered content with every delta and the whole archived proposal; integrate living knowledge at the exact owner, remove obsolete content and archive without adding behavior.
- Read complete affected living docs against [context policy](../context.md): new readers understand purpose/flows without history, each addition changes strategic understanding, inventories stay authoritative, and available capability differs from recommendations. For operations, explain supported topology, state ownership, failure/recovery and monitoring gaps; alert severity/meaning/runbook and metric interpretation link their configuration.
- Required automated checks, applicable independent review and named journey-risk demonstrations must cover the final candidate. Passing coverage establishes execution, not completeness, architecture or conventions.

## Review closure

Architecture and conventions are mandatory gates even without a runtime bug. Review naming, types, declarations, composition, readable density/whitespace, errors, tests, design affinity, necessary seams and behavior before claiming completeness. Do not narrow a review to high-severity runtime findings or pre-label disputed designs as correct.

For a maintainer-reported miss, reopen the failed gate across the complete affected architecture/diff. Independently replay the actual missed design and a valid control against these checks, naming the rule and caller consequence; use the [replay examples](examples.md#review-replays). Adding prose or shortening a misplaced construct without a blocking result is not validation. Repairs and late edits remain open until verified against the exact final candidate; maintainer authorization, not rationale or reviewer discretion, grants exceptions.
